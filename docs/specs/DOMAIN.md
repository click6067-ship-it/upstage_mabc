# DOMAIN.md — 임금·명세서 대조 영역 규칙

## 1. 계산·기록 규칙 (최우선)

- 돈은 **정수 원**, 시간은 **정수 분**으로 다룬다.
- 시간급 산정은 **분 × 시급을 모두 합산한 뒤 60으로 나누고, 마지막에만 원 단위 사사오입**한다.
  - 개별 기록을 미리 원으로 바꿔 합산하지 않는다.
  - 반올림은 **양수 합산분자 기준 정수 산술** `(합산분자 + 30) // 60`으로 처리한다.
  - Python의 `round()`는 사사오입이 아니므로(500.05→500, 166.5→166, 167.5→168 등) 사용하지 않는다.
  - 예: 1분×10,001원 3개 → 합산 30,003 → ÷60 = 500.05 → `(30003 + 30) // 60` = **500원**.
  - 예: 1분×10,050원 1개 → 10,050 → ÷60 = 167.5 → `(10050 + 30) // 60` = **168원**.
  - 예: 1분×9,990원 1개 → 9,990 → ÷60 = 166.5 → `(9990 + 30) // 60` = **167원** (Python round(166.5)와 다름).
- 계산 결과는 참고 산식이며, 체불 확정·법률 판정으로 바로 바꾸지 않는다.
- 같은 문제를 단계별·쟁점별로 분리해 합산하고, **중복 합산하지 않는다**.

## 2. 기간·입금일

- 각 기록은 **급여기간**에 연결한다.
- 급여기간 시작·종료, 입금일(실제 입금 확인일)을 따로 기록한다.
- 예정 입금일과 실제 입금일은 구분한다. 실제 입금 확인 전에는 예정 상태로 둔다.
- 지급은 해당 급여기간에 연결한 것만 다룬다.

## 3. 전월 비교와 기간 수정본

- 전월·당월 비교는 총지급, 공제, 명세서 실지급, 연결 지급(사용자 확인된 지급)만 나란히 놓고 변화를 본다.
- 같은 기간의 수정본·이전 버전 명세서가 있으면 **doc-compare로 항목 차이**를 본다.
  - 비교는 변경 항목과 원문을 찾고, 확인된 값으로 별도 산술을 한다.
  - 법률 판정은 하지 않는다. 모호한 비교는 보류한다.
- 기간 수정본(정정 명세서)을 적용하면 관련 계산·질문·출력도 함께 갱신한다. 정정 전 원문은 보존한다.

## 4. 미확인(null)과 확인됨(0) 구분

- **미확인(null)**: 값이 들어오지 않았거나 사용자가 확인하지 않은 상태. 0으로 채우지 않고 별도 상태로 표시한다.
- **확인된 0**: 사용자가 0임을 확인한 값. 미확인과 구분한다.
- 모르는 값을 0으로 채우지 않는다. 추정·누락·미확인은 별도 상태로 표시한다.

## 5. 지급 합산 규칙

- 지급은 **사용자가 확인한 급여 배분만 합산**한다.
- 다음 가능성을 따로 확인한다.
  - **중복 지급**: 같은 명목이 두 번 연결되지 않았는지 확인.
  - **분할 지급**: 한 급여기간의 급여가 여러 차례 나눠 들어왔는지 확인.
  - **현금 지급**: 계좌 이체 외 현금 지급 여부 확인.
  - **미배분**: 연결되지 않은 지급·항목이 남아 있는지 확인.
- **예정 근무·지급 약속을 실제로 합산하지 않는다.** 약속은 약속대로 따로 표시하고, 실제 지급 확정 후에만 합산 대상에 넣는다.
- 실제 지급 거래는 **양수**로만 다룬다. 0원 수령 확인은 실제 지급과 다른 별도 상태다.

## 6. 분리해서 다루는 산술

- **명세서 내부 산술**: 명세서 항목끼리 합산·차감하여 명세서 totals를 확인하는 산술.
- **지급 차이**: 명세서 실지급액에서 해당 급여기간에 확인해서 배분한 지급만 뺀 차이. 해당 기간에 연결·확인되지 않은 지급은 뺄셈에 넣지 않는다.
- **기본급 참고 산술**: 시간·시급 등 입력 조건에 따른 기본급 참고치.
- 위 세 산술은 서로 혼동하지 않고 각각 결과를 남긴다. 어느 산술 결과도 곧바로 체불 확정으로 바꾸지 않는다.

## 7. 하지 않는 것 (제외)

- **시급 임의 역산**: 임의의 시급을 만들어 역산하지 않는다.
- **최저시급 자동 대입**: 알 수 없는 시급에 최저시급을 자동으로 대입하지 않는다.
- **법정 수당 판정**: 앱이 법정 수당 해당 여부를 판정하지 않는다.
- **차액 → 체불 자동 확정**: 차이를 곧바로 체불로 확정하지 않는다.
- **중복 합산**: 같은 문제를 중복해서 합산하지 않는다.

## 8. 원문에서 종결까지 흐름

```
원문(명세서·지급·기록)
  → 사용자 확인(미확인/확인됨 분리, 항목·금액·날짜 확인)
  → 비교·산술 (명세서 내부 산술 / 지급 차이 / 기본급 참고 산술 분리)
  → 설명·질문 (차이·미확인·남은 의문 정리, 중복 합산 금지)
  → 양언어 출력의 정정 영향 (한국어 + 선택 언어, 같은 사실·같은 버전)
  → 답변·보완 요청·수정 명세서 연결
  → 사용자 확인 후 쟁점별 정리
  → 답변·추가 지급 반영 (실제 지급으로 반영, 남은 의문 재정리)
  → 사용자 종결 상태 (약속=입금 또는 차액 0 = 자동종결로 처리하지 않음)
```

- 정정 전 원문·이력은 보존한다.
- 정정은 화면·양언어·출력 파일까지 이어지고 금액과 버전이 일치해야 한다.
- 예전 출력은 구버전으로 표시한다.
- 미기록 날짜를 실제 근무로 자동 확정하지 않는다.
- 종결(user_closed)은 사용자가 이유와 함께 선택한다. 차액 0이라도 자동 종결하지 않는다.
- 종결 후 새 근거가 오면 종결 상태를 유지하고 새 근거를 별도 표시한다. 사용자가 다시 열면 reviewing으로 돌아간다.
- 기록만 시작한 사람에게는 의문을 자동 생성하지 않는다.

## 9. 상태 구분

- **지급 약속**: 입금 약속만 확인된 상태. 실제 지급과 구분.
- **실제 지급**: 사용자가 확인한 실제 입금액. 합산 대상. 실제 지급 거래는 **양수**로만 다룬다. 0원 수령 확인은 별도 상태다.
- **남은 의문**: 아직 확인·정리되지 않은 쟁점.
- **종결 상태**: 사용자 확인으로 정리된 상태. 차액 0 또는 약속 이행만으로 자동 종결하지 않는다.

### 9.1 의문별 상태 전이 표

| 현재 상태 | 사용자 행동 | 다음 상태 | 금액 영향 |
|---|---|---|---|
| preparing(준비) | 확인 질문을 저장하고 자료를 요청함 | waiting_evidence(자료 대기) | 산정 보류 유지, 입력값만 보존 |
| waiting_evidence | 새 자료(명세서·사진·PDF·기록)를 확인함 | reviewing(재검토) | 새 자료는 항목·금액·날짜별로 확인 후 반영, 기존 확인값과 병존 가능 |
| preparing / reviewing | 설명(검토 결과·분리 항목)을 검토함 | explained(설명 검토 완료) | 산정 결과는 참고치로 유지하며 체불·차액 확정으로 바꾸지 않음 |
| explained / reviewing | 문의나 상담을 선택함 | action_ready(문의·상담 준비 완료) | 지급 약속·실제 지급·남은 의문을 따로 표시, 약속은 합산하지 않음 |
| action_ready | 실제 연락했다고 사용자가 기록함 | waiting_reply(답변 대기) | 약속만 왔으면 reviewing으로 돌아가고, 실제 지급은 양수 확인 후에만 반영. PDF 다운로드만으로는 연락 완료로 보지 않음 |
| waiting_reply / reviewing | 답변·보완 요청·지급 약속을 받음 | reviewing | 지급 약속은 합산하지 않고 약속 상태로만 표시. 실제 지급 약속은 입금액에 합산하지 않음 |
| waiting_reply / reviewing | 실제 지급(양수)이 확인됨 | reviewing (남은 의문 재정리) | 실제 지급은 급여 귀속 확인 후 결과 버전을 갱신. 다른 의문은 유지 |
| reviewing / explained / action_ready | 사용자가 이유와 함께 종료를 선택함 | user_closed(종결) | 자동 종결 조건 아님. 차액 0이더라도 자동종결하지 않음 |
| user_closed | 닫은 뒤 새 근거가 들어오면 | user_closed 유지 + 새 근거 표시 | 종결 상태는 유지, 새 근거는 별도 표시 |
| user_closed | 사용자가 다시 열면 | reviewing | 남은 의문을 다시 검토 |
| (기록만 시작한 사람) | 별도 의문 생성 요청 없음 | 의문 자동 생성 안 함 | 기록만 시작한 사람에게 의문을 자동 생성하지 않음 |
| **위 상태 전부 (종결 전)** | 실제 지급(양수)이 확인됨 | reviewing (남은 의문 재정리) | 실제 지급은 급여 귀속 확인 후 결과 버전을 갱신. 다른 의문은 유지. 종결 전 어느 상태에서든 실제 지급 확인이 가능하다 |
| **위 상태 전부 (종결 전)** | 사용자가 이유와 함께 종료를 선택함 | user_closed(종결) | 자동 종결 조건 아님. 차액은 체불로 자동 확정하지 않음. 종결 이유는 "지급 해결"과 "단순 중단"을 구분해 기록한다 |

### 9.2 상태 전이 예외 규칙

- 설명 검토(explained)와 문의·상담 선택(action_ready)은 서로 다른 진입점이 있다. 설명만 검토하고 문의·상담을 선택하지 않을 수 있다.
- waiting_reply에서 답변·보완 요청·지급 약속이 오면 reviewing으로 돌아간다. 약속은 입금액에 합산하지 않는다.
- 실제 지급은 **양수** 거래만 반영한다. 0원 수령 확인은 실제 지급과 다른 별도 상태다.
- PDF 다운로드만으로는 연락 완료로 보지 않는다. 실제 연락 여부는 사용자가 직접 기록해야 한다.
- 종결(user_closed)은 사용자가 **이유와 함께** 선택한다. 차액 0이라고 자동 종결하지 않는다.
- 종결 이유는 "지급 해결"과 "단순 중단"으로 구분한다.
  - "지급 해결": 실제 지급(양수)을 확인하고 급여 귀속까지 확인한 경우에만 선택한다. 지급 약속만 있는 상태는 지급 해결로 처리하지 않는다.
  - "단순 중단": 더 확인하지 않고 중단, 보류 등 사유로 마무리할 때 선택한다.
- 이유를 선택하지 않은 종결은 허용하지 않는다. 사용자는 종결 전에 이유를 선택해야 한다.
- 종결 후 새 근거가 오면 종결 상태를 유지하고 새 근거를 별도 표시한다. 사용자가 다시 열면 reviewing으로 돌아간다.
- 기록만 시작한 사람에게는 의문을 자동 생성하지 않는다.

## 10. 합성 사례 A — 전월→당월 비교

### 10.1 입력값

| 항목 | 전월 | 당월 |
|---|---|---|
| 총지급 | 2,400,000원 | 2,300,000원 |
| 공제 | 200,000원 | 250,000원 |
| 명세서 실지급 | 2,200,000원 | 2,050,000원 |
| 연결 지급(사용자 확인분) | 2,200,000원 | 2,030,000원 |

### 10.2 월간 변화

- 총지급: 2,300,000 − 2,400,000 = **−100,000원**
- 공제: 250,000 − 200,000 = **+50,000원**
- 명세서 실지급: 2,050,000 − 2,200,000 = **−150,000원**
- 연결 지급: 2,030,000 − 2,200,000 = **−170,000원**

### 10.3 명세서 실지급 − 연결 지급 차이

- 전월: 2,200,000 − 2,200,000 = **0원**
- 당월: 2,050,000 − 2,030,000 = **20,000원**
- 전월 대비 변화: 0 → 20,000 (**+20,000원**)

### 10.4 이 사례에서 남는 분리 항목

- 지급 차이(명세서−연결): 당월 20,000원 발생. 전월은 0.
- 당월 연결 지급 2,030,000원은 **확인된 입력값**이다. 미확인 부분은 이 2,030,000원 자체가 아니라 **그 차이 20,000원의 원인**이다.
- 월간 변화: 총지급 −100,000, 공제 +50,000, 명세서 실지급 −150,000, 연결 지급 −170,000.
- 남은 질문: 명세서 실지급과 연결 지급 사이 20,000원 차이의 원인 항목. 공제 증가 50,000원과 총액 감소 100,000원의 관계.

### 10.5 중복 합산 금지 지점

- 월간 변화 항목과 명세서−연결 차이를 합쳐서 "최종 차이"로 중복 선언하지 않는다.
- 각 줄은 별도 쟁점으로 남긴다.

## 11. 합성 사례 B — 기본급 시간 정정 (5단계 분리)

### 11.1 공통 입력

- 시급: 시간당 12,000원 (정수). 시간은 **정수 분** 단위로 다룬다.
  - 152시간 = 9,120분
  - 160시간 = 9,600분
  - 158시간 = 9,480분
- 기타: 384,000원 (정수). 수정 명세서 적용 단계에서도 그대로 유지.
- 공제: 208,000원 (정수). 수정 명세서 적용 단계에서도 그대로 유지.
- 명세서 기본급(단기): 명세서 기준 시간 × 시급 ÷ 60, 마지막에만 사사오입.
- 명세서 합계: 명세서 기본급 + 기타 − 공제.

### 11.2 단계별 상태

| 단계 | 명세서 기준 시간 | 실제 지급 | 명세서 기본급 | 명세서 합계 | 지급 차이 | 기본급 참고 산술 차이 |
|---|---|---|---|---|---|---|
| 1. 원본 | 9,120분 | 1,980,000 | 1,824,000 | 2,000,000 | 20,000 | null |
| 2. 추가 지급 | 9,120분 | 2,000,000 | 1,824,000 | 2,000,000 | 0 | null |
| 3. 160시간 확인 | 9,120분 | 2,000,000 | 1,824,000 | 2,000,000 | 0 | 96,000 |
| 4. 158시간 정정 | 9,120분 | 2,000,000 | 1,824,000 | 2,000,000 | 0 | 72,000 |
| 5. 수정 명세서 적용 | 9,480분 | 2,000,000 | 1,896,000 | 2,072,000 | 72,000 | 0 |

### 11.3 단계별 설명

1. **원본**
   - 명세서 기본급 1,824,000원, 합계 2,000,000원.
   - 실제 지급 1,980,000원 → 지급 차이 20,000원.
   - 지급 차이를 체불로 확정하지 않는다.
   - 기본급 참고 산술은 아직 연결되지 않음(null).

2. **추가 지급**
   - 같은 급여에 20,000원 추가 지급을 사용자가 확인함.
   - 실제 지급 2,000,000원으로 반영. 명세서는 원본 그대로.
   - 지급 차이 0. 기본급 참고 산술 null.
   - B1/B2 모두 지급 차이는 계산 가능(각각 20,000원, 0원), 기본급 참고 산술은 보류(null).

3. **160시간 확인**
   - 해당 기본급의 실제 근무시간 160시간(9,600분)을 확인함.
   - 명세서는 아직 원본(9,120분) 기준.
   - 지급 차이 0.
   - 기본급 참고 산술 차이: 9,600분 × 200원 − 9,120분 × 200원 = 96,000원.
   - 이 96,000원은 명세서 기본급과의 참고 산술 차이이며, 자동 추가 지급 확정이 아니다.

4. **158시간 정정**
   - 160시간에서 158시간(9,480분)으로 정정함.
   - 명세서 아직 미적용.
   - 지급 차이 0.
   - 기본급 참고 산술 차이: 9,480분 × 200원 − 9,120분 × 200원 = 72,000원.

5. **수정 명세서 적용**
   - 158시간 기준 수정 명세서를 명시적으로 적용함.
   - 수정 기본급: 9,480분 × 200원 = 1,896,000원.
   - 수정 명세서 합계: 1,896,000 + 384,000 − 208,000 = 2,072,000원.
   - 지급 차이: 2,072,000 − 2,000,000 = 72,000원.
   - 기본급 참고 산술 차이: 0 (명세서와 확인된 시간이 같아짐).
   - 기타·공제는 그대로.

### 11.4 분리 규칙

- 시간만 고쳤다고 수정 명세서를 자동 적용하지 않는다. 5단계는 명시적 적용이다.
- 원본 지급 차이 20,000원과 정정 후 차이 72,000원은 별개 쟁점이다. 중복 합산하지 않는다.
- 기본급 참고 산술 차이(96,000 / 72,000)는 명세서 기본급이 바뀌지 않은 단계에서는 참고치다.

### 11.5 미확인·남은 질문

- 160시간 확인 근거(기록·증빙)와 158시간 정정 근거 분리 필요.
- 추가 20,000원이 어떤 항목 보정인지 사용자 확인 필요.
- 기타·공제가 정말 그대로인지 재확인.

## 19. 지급 배분 규칙

- 한 입금을 여러 급여기간에 나눠 배분할 수 있다. 단, **배분 합계는 입금액 이하**여야 한다.
- 배분 합계가 입금액보다 작으면 나머지는 **미배분**으로 남긴다.
- 배분 합계가 입금액을 넘으면 그 배분은 적용 불가로 본다.
- **같은 지급을 다시 업로드해도 중복 합산하지 않는다.** 동일 지급 식별이 확인되면 추가 합산 대신 재업로드로 처리한다.
- 다른 캡처·현금 수령은 사용자 확인이 필요하다. 확인 전에는 지급 합계로 넣지 않는다.

### 19.1 입력 예시 1 — 분할 배분, 미배분 발생

- 입금액: 100,000원 (사용자 확인 완료).
- 배분:
  - 급여기간 A: 60,000원
  - 급여기간 B: 30,000원
- 미배분: 100,000 − (60,000 + 30,000) = 10,000원.

결과:

- 배분 합계 90,000원 ≤ 입금액 100,000원 → **계산 가능**.
- 미배분 10,000원은 별도 상태로 표시. 0으로 채우지 않음.
- 총지급·차이 계산 시 미배분을 임의로 넣지 않는다.

### 19.2 입력 예시 2 — 배분 과다, 적용 불가

- 입금액: 100,000원 (사용자 확인 완료).
- 배분:
  - 급여기간 A: 60,000원
  - 급여기간 B: 50,000원

결과:

- 배분 합계 110,000원 > 입금액 100,000원 → **보류/적용 불가**.
- 합계가 입금액을 넘는 배분은 계산하지 않는다. 사용자에게 재배분 확인 필요.

### 19.3 입력 예시 3 — 같은 지급 재업로드

- 동일 입금 200,000원을 두 번 업로드.
- 동일 지급 식별이 확인되면:
  - 첫 업로드분만 합산 대상.
  - 두 번째 업로드는 중복 합산하지 않음.
- 동일 지급 식별이 확인되지 않으면 **보류**.

### 19.4 입력 예시 4 — 다른 캡처/현금 수령

- 계좌 이체 150,000원 + 현금 20,000원(사용자 미확인).
- 결과:
  - 계좌 이체 150,000원: **계산 가능**(사용자 확인분).
  - 현금 20,000원: **보류**(사용자 확인 전).
  - 총지급 합산 시 현금 20,000원은 넣지 않음.

## 23. 시급·반복 패턴·역산 금지

- 시급과 반복 패턴은 **적용일을 확인**한다.
- 과거 기록을 자동으로 변경하지 않는다.
- 월급·일급을 시급으로 역산하지 않는다.
- 시급이 겹치면 **보류**.
- 변경구간이 확인되면:
  - 구간별로 분 × 시급을 합산한 뒤, **마지막에만 반올림**.

### 23.1 입력 예시 1 — 적용일 확인 필요

- "시급 12,000원"이라고 적혀 있음.
- 적용일(언제부터 적용) 미확인.
- 결과: **보류**. 과거 기간에 자동 적용하지 않음.

### 23.2 입력 예시 2 — 월급→시급 역산 금지

- 월급 2,400,000원, 근무 200시간.
- 결과:
  - 이 정보만으로 시급을 계산하지 않음.
  - 시급은 별도 입력·확인 전에는 계산하지 않음.

### 23.3 입력 예시 3 — 시급 겹침

- 동일 기간에 시급 12,000원과 13,000원이 함께 기록됨.
- 결과: **보류**. 어느 시급을 적용할지 확인 전 계산 확정하지 않음.

### 23.4 입력 예시 4 — 변경구간 확인, 반올림은 마지막에만

- 구간 1: 30분 × 12,000원.
- 구간 2: 30분 × 14,000원.
- 결과:
  - 합산분자: 30×12,000 + 30×14,000 = 360,000 + 420,000 = 780,000.
  - 사사오입: `(780000 + 30) // 60` = **13,000원**.
  - 구간별 반올림 후 합산하지 않음(마지막에만 반올림).

## 25. 정정 버전 규칙

- **원문/추출 후보/사용자 확인값은 별개**로 다룬다.
  - 새 파일(명세서·PDF·사진)을 올렸다고 기존 확인값을 자동 교체하지 않는다.
  - 추출 후보(OCR/AI 등)는 후보일 뿐이며, 사용자 확인 전에는 확정값으로 쓰지 않는다.
- **수정본 적용은 사용자 확인 후**에만 반영한다.
  - 적용 전 원문·이력은 보존한다.
- **확인값 변경과 새 결과 버전 저장은 함께 성공**해야 한다.
  - 확인값이 바뀌면 관련 계산·비교·결과 버전도 같은 시점에 새 버전으로 저장한다.
  - 예전 입력에 대한 늦은 OCR/AI 응답이 최신 확인값을 덮으면 안 된다.
- **정정하면 같은 버전으로 연결해서 갱신**한다.
  - 비교·계산·질문·설명·한국어와 선택 언어·출력 파일까지 같은 버전으로 맞춘다.
  - 무관한 다른 달·다른 기간 변경은 같이 바꾸지 않는다.
- **내려받은 PDF는 소급 수정 불가**로 다룬다.
  - 앱에서 구버전으로 표시하고, 필요 시 새 파일을 생성하는 방식으로 처리한다.
  - 기존 내려받은 PDF 내부 값을 앱 단정만으로 고치지 않는다.

### 25.1 정상 흐름 예시

- 사용자가 수정된 명세서(PDF)를 업로드함.
- 원문(기존 업로드 명세서)과 새 파일은 별도 기록.
- 사용자가 새 파일을 "이번 기간 정정본"으로 확인함.
- 확인 직후:
  - 확인값과 새 결과 버전을 함께 저장한다.
  - 설명, 번역, 출력 PDF는 생성 대기 상태로 둘 수 있다.
  - 정정 전 원문은 보존한다.
- 생성/검토가 끝난 항목만 최신 결과로 보여준다. 생성 대기·실패 상태인 설명/번역/출력은 최신 결과로 표시하지 않는다.
- 결과: 확인값과 결과 버전은 저장되고, 설명/번역/출력은 생성 완료 후에 최신 결과로 제공된다.

### 25.2 예외 결과 예시 1 — 늦은 응답

- 사용자가 A 기간 값을 확인·저장함(버전 2).
- 이후 예전 입력(A 기간)에 대한 OCR/AI 응답이 늦게 도착함.
- 결과:
  - 늦은 응답이 버전 2 확인값을 덮지 않음.
  - 늦은 응답은 후보/별도 기록으로 남기거나, 사용자 재확인 전까지 미반영.

### 25.3 예외 결과 예시 2 — 출력 재생성

- 정정 반영 후 출력(선택 언어 포함)을 재생성함.
- 결과:
  - 재생성된 출력은 새 버전으로만 제공.
  - 구버전 출력은 구버전으로 표시.
  - 새 정정과 무관한 다른 기간 출력은 재생성 대상이 아님(요청된 범위만).

### 25.4 저장 시점 규칙 — 같은 시점에 확인값과 결과 버전까지 함께 저장

- 확인값이 바뀌면 **확인값과 새 결과 버전을 함께 저장**한다. 둘 중 하나만 먼저 저장하지 않는다.
- 확인값과 새 결과 버전은 함께 저장하되, **설명/번역/출력 PDF는 생성 대기나 실패 상태가 가능**하다. 대기·실패 상태는 별도 표시하며, 확인값 자체를 rolled back하지 않는다.
- 최신 버전으로 생성·검토되기 전 구버전을 최신으로 표시하지 않는다.
- 저장에 실패하면 **이전 확인값과 이전 버전을 유지**한다. 부분 저장(반만 성공한 상태)으로 두지 않는다.

## 26. 입력 경계 (정상 범위와 예외 처리)

### 26.1 정상 입력 범위

- **돈**: 정수 원, 절댓값 **999,999,999 이하**.
- **시급**: 정수, **1 이상 1,000,000 이하** (시간당 원).
- **근무 한 구간**: 정수 분, **0 이상 1,440 이하**(24시간). 종료 시점은 시작 시점으로부터 **최대 다음날까지** 허용한다.
- **실제 지급 거래**: **양수**만 정상 값으로 다룬다. 0원 수령 확인은 실제 지급과 다른 별도 상태다.
- **문서에 적힌 음수 조정액/차이**: 부호를 보존한다. 절댓값으로 덮어쓰지 않는다.

### 26.2 범위 밖 입력 — 자료 보존 + 산술 보류

- 정상 범위를 벗어난 값은 **입력 자료를 보존**하고, 관련 자동 산술은 **보류**한다.
- 예를 들어 시급이 0 이하이거나 1,000,000을 넘으면 시급 입력을 보존하되, 해당 값을 쓴 기본급 참고 산술은 계산하지 않는다.
- 근무 구간이 1,440분을 넘거나 종료 시점이 다음날부터 더 멀리 가면 해당 구간 입력을 보존하되, 그 구간을 쓴 근무시간·급여 산정은 보류한다.
- 돈 값이 절댓값 999,999,999를 넘으면 자료를 보존하고, 그 값을 넣은 합산·차이는 보류한다.

### 26.3 0분 확인과 미기록 구분

- **확인된 0분**: 사용자가 "이 구간은 근무 0분이다"라고 확인한 상태. 미기록과 구분한다.
- **미기록**: 기록이 없는 상태. 0분으로 채우거나 결근으로 자동 확정하지 않는다.
- 두 상태는 별도 상태로 표시한다.

### 26.4 실제 지급과 0원 수령

- 실제 지급 거래는 **양수**로만 다룬다.
- **0원 수령 확인**은 실제 지급과 다른 별도 상태다. "0원 받았다"는 확인이 들어오면 실제 지급 합계에는 넣지 않고 별도 상태로 남긴다.
- 실제 지급으로 반영하려면 양수 확인 + 급여 귀속 확인이 필요하다.

### 26.5 절삭·환산 금지

- 문자·소수·외화를 임의로 절삭하거나 환산해서 계산하지 않는다.
- "대략 1,200,000원 정도", "약 500달러" 등 모호한 입력은 그대로 보존하고, 자동 계산에는 넣지 않는다.
- 외화 입력은 원화 환산을 자동 적용하지 않는다. 환산이 필요하면 사용자 확인값과 적용 시점을 별도로 기록한다.

### 26.6 중간 곱·합의 안전한 정수 계산 범위 확인

- 분 × 시급, 합계, 차이 등 **중간 곱과 합도 정수 계산 범위를 확인**한다. 이 확인은 돈 상한(999,999,999)과 별개다.
- 중간 곱 자체는 돈 상한을 넘길 수 있다. 예를 들어 1,440분 × 1,000,000원 = 1,440,000,000은 중간 곱 단계에서 돈 상한보다 크지만, ÷60 후 사사오입하면 24,000,000원이 되어 계산 가능하다.
- 중간 계산 중 최종 결과가 정상 범위를 벗어나면 그 계산을 보류하고, 어느 단계에서 범위를 넘었는지 남긴다.
- 최종 결과만 확인하는 것이 아니라, 중간 분·구간·시급 곱과 누적 합도 정수 계산 범위 안으로 유지되는지 확인한다.

### 26.7 최저시급 참고

- **최저시급 참고는 사용자가 명시로 선택한 경우에만** 사용한다.
- 또한 **해당 기간의 공식값 확인 후에만** 참고치로 쓴다.
- 알 수 없는 시급에 최저시급을 자동으로 대입하지 않는다.

### 26.8 명세서 기재 실지급액 vs 내부 계산값

- 명세서에 적힌 실지급액과 내부에서 계산한 값이 다르면 **둘 다 보존**한다.
- 지급 비교는 **사용자가 확인한 명세서 기재액 기준**으로 한다. 내부 계산값으로 기재액을 덮어쓰지 않는다.
- 차이가 나면 그 차이는 별도 쟁점으로 남기고, 어느 값이 기준인지 명시한다.

### 26.9 정상 사례 / 예외 사례 요약

**정상 사례**
- 시급 12,000원, 근무 9,120분(여러 구간의 급여기간 합계, 한 구간이 아님) → 범위 안 → 계산 진행.
- 실제 지급 2,000,000원(양수) 확인 → 지급 반영.
- 명세서 기재 실지급액 2,000,000원과 내부 계산값 2,000,000원이 같음 → 비교 진행.
- 명세서에 적힌 차이 −20,000원 → 부호 보존, 별도 쟁점으로 남김.

**예외 사례**
- 시급 0원 → 범위 밖 → 자료 보존, 기본급 참고 산술 보류.
- 근무 구간 1,500분 → 범위 밖 → 자료 보존, 그 구간 산정 보류.
- "약 1,200,000원" → 문자·모호 입력 → 보존, 자동 계산 보류.
- 외화 500달러만 입력 → 환산 보류, 사용자 확인 전 계산에 넣지 않음.
- 0원 수령 확인 → 실제 지급 합계 미합산, 별도 상태.
- 명세서 기재액 2,000,000원 vs 내부 계산값 2,072,000원 → 둘 다 보존, 비교는 기재액 기준.
